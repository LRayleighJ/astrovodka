验证记录

本页记录 astrovodka 中的 HI/H₂ 模型是如何验证的。这里要支持的结论很窄、 也很具体：物理与参考实现逐位（bit for bit）一致，而建立在其上的 观测流水线守恒质量，并把天体放在正确的距离上。

这里没有任何东西需要你凭信任接受 —— 每一项检查要么是 tests/ 里的 一个测试，要么是一条你可以重新运行的命令。

验证的是什么

这四个模型是已发表方案的实现，而不是新的物理：

hi_model 方案 投影
GD14_vol Gnedin & Draine (2014)，附录 C.3 体密度
GD14_map Gnedin & Draine (2014)，§2.3 投影
K13_vol Krumholz, McKee & Tumlinson (2013)，附录 C.4 体密度
K13_map Krumholz+ (2013)，§2.3 投影

以上均按 Diemer+2018 (arXiv:1806.02341) 的方式组装。

因此问题不是“物理对不对” —— 那由这些论文来定 —— 而是 “这段代码是否和参考实现是同一段代码”。所以才强调精确一致， 而不是强调看起来合理的数字。

这条链条是：Diemer+2018 的参考实现 （TNGHI_GD14_model/gd14_model.py）→ TNGHIcalc 包 → astrovodka.himodel。 每个箭头都是通过在相同输入上重新运行两边来检查的。

测试套件

python -m pytest tests/ -q      # 125 个测试，约 14 s

它不需要 TNG 数据，不需要网络，也不需要任何可选依赖。

0.2.0 和 0.3.0 中修复的每一个缺陷都有一个回归测试。

其中有两个测试值得一说，因为最显然的写法并不会抓住那些 bug：

  • 0.2.0 的光谱宽度测试断言的是数值，而不是单位。原来的测试只检查了 轴是否携带*某个*频率单位，这就是为什么一个只留下 0.007% 流量的 数据立方体连续两个版本都蒙混过关了。
  • 0.3.0 的 FFT UV 回归测试基于位置，而不是一个钉死的数值。 插值器一旦坏掉，无论源恰好落在哪里都会返回背景，因此值得断言的 性质是“场对源所在的位置有响应” —— 钉死一个数值的话，同样的故障 换个网格排布就能再溜回来。

与参考实现逐位一致

物理表达式是逐字移植的 —— 连操作数顺序也一并保留，因为一致性正建立在 这上面。下面的比较都是在移植之后重新运行的：

比较 结果
每一个 himodel.physics 函数对 TNGHIcalc，在跨越物理范围的 4000 个随机单元上（h = 0.6774，z = 0.5） 12/12 np.array_equal
compute_hi_mass 对 TNGHIcalc.cells_vol / cells_map，全部四种方法，合成星系置于偏心位置 质量、f_mol、U_MW 和 row_index 逐位精确
全部四种方法在真实 TNG-100 snap 99 子晕 122（4448 个单元）、7（120 个单元）和 4（86902 个单元）上 逐位精确

为什么单位换算值得单开一段

rho_code_to_physical 刻意走 astropy 的单位链，而不是乘一个硬编码的 常数。两者并不相同：astropy 的 kpc 是 3.0856775814913673 × 10²¹ cm， 而模块自带的 kpc_to_cm 是 3.08568 × 10²¹ cm —— 相对差异约 8 × 10⁻⁷。把一个换成另一个，会让每一个密度都在 10⁻⁶ 的量级上发生 无声的改变，而这个改变会传播到每一个分子比例里。

这正是逐位精确比较能抓住、而抽查抓不住的那一类错误，所以才要对它 做断言。

移植顺带移除的一个陷阱

参考实现的 f_mol_* 函数把 z = 0.0 当作一个带默认值的位置参数。 因此不传红移就调用它并不会失败 —— 它会用零悄悄覆盖掉配置好的红移。 在 himodel 中，红移只来自 HIModelConfig， 没有可以掉进去的位置默认值。

在真实数据上的端到端检查

TNG-100 快照 99，子晕 122，通过 TNGSource 构建：

GD14_vol 2.4169 × 10⁹ 1.0397 × 10⁹ 100%

GD14_map 2.1310 × 10⁹ 1.2287 × 10⁹ 100%
K13_map 3.0689 × 10⁹ 2.9075 × 10⁸ 100%

投影模型把 88.3% 的气体质量装在投影盒内，因此有 474 个单元得到零质量。 这些单元在插入数据立方体之前会被自动裁剪掉，而立方体的 M_HI 仍然精确等于 source.m_HI_total —— 这正是关键所在：零质量的单元 从不贡献流量，因此回收率保持在 100%。

选择演示子晕

教程使用 TNG-100 快照 99 的子晕 113。它是通过实测候选者选出来的， 而不是随便取 HI 最多的那一个。

要求是既有 HI *又有*恒星形成。自适应 FFT 紫外场只在有恒星形成的气体里 才做得出看得见的工作，因此一个富气体但不活跃的子晕说明不了它 —— 之前的演示子晕在这方面尤其糟糕：模型在整个 120 个气体单元里只给它 大约 16 M☉ 的 HI，而且完全没有恒星形成，这使它的数据立方体 出于一个纯物理的原因被噪声主导。

子晕 139 的 HI 多 5%，但它的 UV 场峰值只比背景高出约 1550 倍， 因此在它上面，0.3.0 修掉的那个 bug 所属的模型看起来会和坏掉的那个 几乎一模一样。子晕 113 还把 95.5% 的气体留在投影盒内， 这让 *_map 模型之间可以直接比较。

在 z = 0.02 下端到端实测：两个立方体的质量回收都是 100%， 10 arcsec 波束的 moment-0 峰值 S/N 为 5.5、总流量 S/N 为 16.9， 3 arcmin 波束为 6.5。

复现这些检查

# 1. 单元测试 —— 不需要 TNG 数据
python -m pytest tests/ -q

# 2. 教程，它会在运行过程中对自己的结果做断言
#    （先把路径指向你的 TNG 数据）
export TNG_BASE_PATH=/path/to/TNG/TNG-100/
#    ... 然后运行 examples/{en,zh}/tutorial_TNG100-HI-mock-observations.ipynb

教程中有好几节带有 assert 语句，而不是打印数字让读者自己看： 质量回收必须是 100%，积分后的 FITS 流量必须复现模型自己的总量、 误差在 1% 以内，速度轴和频率轴两个立方体的流量必须一致。 如果某项改动破坏了物理，那份 notebook 会失败， 而不是悄悄报出另一个数字。
